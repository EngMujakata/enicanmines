The architecture is actually quite clear: IndexedDB is the local operational database, Google Apps Script/Sheets is the central database, and the sync queue bridges the two. The frontend is also fairly substantial—dashboard, loading, emptying/payment, sessions, reports, audit trail and settings are all present. 1. Overall architecture Your system is essentially: ┌──────────────────────┐ │ Enican Mines UI │ │ index.html │ └──────────┬───────────┘ │ Local-first operation │ ┌──────────▼───────────┐ │ IndexedDB │ │ tanks │ │ customers │ │ invoices │ │ sessions │ │ expenses │ │ payments │ │ auditTrail │ │ syncQueue │ └──────────┬───────────┘ │ Internet │ ┌──────────▼───────────┐ │ Google Apps Script │ │ code.gs │ └──────────┬───────────┘ │ ┌──────────▼───────────┐ │ Google Sheets │ │ Tanks │ │ Customers │ │ Invoices │ │ Sessions │ │ Expenses │ │ SessionExpenses │ │ Payments │ │ AuditTrail │ │ ProcessedWrites │ │ Users │ └──────────────────────┘ The backend creates/maintains those Sheets automatically. The local-first idea is good. The application can continue working locally and place writes into syncQueue, while the backend uses ProcessedWrites to avoid processing the same write twice. 2. What the system currently does Authentication The backend has: authenticateUser() getUsers() roles: admin and operator persistent frontend login using localStorage The intended backend authentication function does correctly look through the Users sheet for matching credentials. But there is a major security problem, discussed below. Tank management You have: tank creation automatic bulk tank creation active/inactive tanks vacant/occupied/ready-to-empty states tank dashboard tank utilisation Bulk creation is performed directly by the Apps Script backend. Loading The loading workflow is: Invoice ↓ Customer ↓ Select vacant tanks ↓ Add expenses ↓ Calculate cost/selling/profit ↓ Create sessions ↓ Mark tanks OCCUPIED ↓ Create audit ↓ Put everything into syncQueue That's a sensible workflow. The frontend creates the invoice, customer, sessions, session expenses and tank updates locally, then creates one sync package containing those records. Emptying The emptying workflow is: Find invoice ↓ Enter payment ↓ Confirm payment ↓ Complete sessions ↓ Make tanks VACANT ↓ Create audit ↓ Queue synchronization The payment and tank/session changes are bundled into the sync operation. Reports Reports calculate: revenue costs profit customer filtering date filtering status filtering tank utilisation financial charts The report calculation is done from the local IndexedDB session data rather than directly from Sheets. 3. The biggest problem: security This is the number-one thing I would fix before putting this into real operational use. Your frontend login does not actually use the backend authenticateUser() function. Instead, it calls: action: "getUsers" and receives the entire Users table. Then the browser does: data.users.find( u => u.username === username && u.password === password ) So the browser receives usernames and plaintext passwords. The frontend also stores those users in IndexedDB. That means your authentication is effectively: Browser ↓ "Give me every user and their password" ↓ Browser checks password rather than: Browser ↓ username + password ↓ Server authenticates ↓ server returns safe user identity Worse: the backend actions aren't authenticated doPost() accepts actions such as: getUsers getAllData autoAddTanks syncWrite without requiring a valid authenticated session/token. So someone who knows the Web App URL can potentially POST directly to it without going through your UI. And autoAddTanks() itself doesn't check the user's role. That means hiding the Settings button from operators is UI security, not backend security. 4. There is an even worse admin-password problem You have this in the frontend: if (pwd === "admin") The administrator authentication modal therefore has a hardcoded password in index.html. So even if the main login were secure, this creates another bypass. Also, because currentUser is stored in localStorage, someone can manipulate the browser's local storage and potentially make themselves appear to be: { username: "...", role: "admin" } The frontend then trusts that value. So the current role system should be considered presentation-level only. 5. Very important: Settings changes aren't actually synchronized I found a functional problem that is probably going to surprise you. For example: addNewTank() does: IndexedDB → add tank and then calls: triggerSyncQueueProcess() But it does not create a syncQueue record first. The same problem exists with: activating/deactivating tanks adding predefined expenses activating/deactivating expenses For example, addNewPredefinedExpense() puts the expense into IndexedDB and then attempts to process the queue, but doesn't itself add the expense to the queue. Therefore: Adding a tank Browser ↓ IndexedDB ↓ Tank exists locally Google Sheets ↓ Tank DOES NOT necessarily exist Then fetchLiveData() runs later and clears the local tanks and reloads Sheets. Your newly created tank can disappear. This is a real bug, not merely an architectural concern. 6. Another synchronization problem Your fetchLiveData() does: clear local tanks clear local sessions clear local expenses clear local customers ... download server copy The frontend explicitly clears those stores before rebuilding them from the server. But your application is simultaneously designed to support offline/pending writes. That creates this possible sequence: User makes change ↓ IndexedDB updated ↓ syncQueue contains change ↓ fetchLiveData() ↓ IndexedDB gets cleared ↓ server copy downloaded If the server hasn't processed the queued write yet, the user's local change temporarily disappears. And you call fetchLiveData() immediately after important operations such as loading and emptying. So the local-first system needs a stronger rule: Never overwrite local pending changes with a server snapshot until the pending queue has been successfully reconciled. 7. Expenses are missing from the backend write processor This is another significant issue. Your backend processClientWritePayload() handles: customers invoices sessions sessionExpenses tanks payments audit but there is no corresponding: if (payload.expenses) { ... } The backend write processor is shown here. So even if you later correctly put predefined expenses into syncQueue, the backend currently wouldn't persist them. This needs to be added. 8. Frontend has data stores the server isn't fully restoring Your IndexedDB has: payments sessionExpenses but fetchLiveData() only restores: tanks sessions expenses customers users auditTrail invoices The retrieved backend response does contain payments and sessionExpenses, but the frontend doesn't repopulate those stores in the shown fetchLiveData() implementation. So you currently have an asymmetry: Sheets ↓ payments sessionExpenses ↓ API response ↓ frontend doesn't fully restore them That should be corrected. 9. Your ID strategy needs improvement This is another important database issue. Customer IDs are generated from customer names: CUST- + customerName So: ABC Mining always becomes something like: CUST-ABC_MINING If the same customer is entered again, you aren't creating a new customer—you are overwriting/updating the same IndexedDB key. That's actually potentially useful if intentional, but it becomes problematic if the name changes slightly: ABC Mining ABC Mining Pvt Ltd ABC Mines These become separate customers. Invoice IDs are even more important You use: INV- + invoiceNumber So invoice number uniqueness is effectively assumed. That's okay if invoice numbers are guaranteed unique, but that should be enforced centrally. Session IDs You use: SESS-{invoice}-{tank} Again, this assumes that the same invoice/tank combination can never be reused. I'd eventually move to UUID-style IDs and treat invoice numbers as business identifiers rather than database primary keys. 10. Your sync architecture is actually one of the strongest parts The concept of: writeId deviceId timestamp payload is good. And the backend maintains: ProcessedWrites to detect duplicate writes. That means if the browser sends: WID-123 and the connection drops after the server processes it, the browser can retry and the server can respond: ALREADY_PROCESSED That is exactly the type of protection you want in an offline-capable business application. The current implementation just needs to be made more robust. 11. Google Sheets is currently acting as the master database The architecture is: IndexedDB = operational/local copy Google Sheets = central source That's actually a reasonable architecture for this size of operation. The backend's getAllData() collects all the major sheets and sends them to the browser. But there is a scalability consideration: Every refresh effectively asks Apps Script to: read entire Tanks read entire Sessions read entire Expenses read entire Customers read entire Users read entire AuditTrail read entire Invoices read entire SessionExpenses read entire Payments As the audit trail and transaction history grow, this will become increasingly expensive. For now, it's workable. Eventually I'd change it to incremental synchronization. 12. The frontend design is quite good From the UI side, I actually like the direction. You have: responsive desktop/mobile layouts mobile bottom navigation desktop navigation slide-out menu dashboard KPIs tank cards progress bars loading workspace emptying workspace live sessions completed sessions reports audit trail administrator settings PWA manifest reference IndexedDB offline storage The overall UI structure is already that of a proper internal business application rather than a basic Google Sheets interface. 13. The business workflow makes sense The intended lifecycle appears to be: VACANT │ │ Load ▼ OCCUPIED │ │ 10-day expected cycle ▼ READY / OVERDUE │ │ Payment + Empty ▼ COMPLETED SESSION │ ▼ VACANT And the tank dashboard derives overdue status from the expected completion date. That's a good model for the cyanidation operation. 14. One thing I would change about payment Currently, when emptying a group of tanks, the user enters a payment amount and the system marks the sessions as completed. But there isn't a strong accounting relationship between: invoice total payment amount amount paid balance The payment is recorded, but the invoice doesn't appear to have a proper: TOTAL PAID BALANCE PAYMENT STATUS ledger. For a mining operation, I'd make this much stronger. For example: Invoice: INV-0042 Total Selling: $2,850 Payments: 2026-10-01 $1,000 2026-10-04 $1,850 Total Paid: $2,850 Balance: $0 Status: PAID That would make your financial reports much more reliable. 15. Another issue: initializeSystem() on every POST Every request enters: initializeSystem(); before processing the requested action. And you acquire a script lock first. So even something simple like: getAllData causes the system to: lock ↓ check every required sheet ↓ check headers ↓ possibly modify sheets ↓ perform requested operation ↓ release lock This is unnecessarily heavy. I'd initialize the database once during setup, or only run schema validation when required. 16. Password storage should be changed Currently the Users sheet is: username password role createdAt updatedAt and passwords are plaintext. For an internal prototype this is understandable, but for the production system I would change this to: username passwordHash role active createdAt updatedAt and authentication should happen entirely on the backend. 17. Bottom line The project is much further along than just a prototype UI. You have a real local-first business application with a central Google Sheets backend, transaction records, audit trail, offline queueing, reports and a proper operational workflow. The biggest issue isn't that the system lacks features. It's that the security and synchronization foundations need to be tightened before you trust it with real operational/financial data. The good news is that I don't think you need to throw this away. The existing architecture can be preserved; I would repair the backend security and sync layer while keeping the current UI and business workflow largely intact. The two files are also clearly separated in responsibility: code.gs is currently a relatively small API/data layer, while most of the actual application intelligence is inside the 1,798-line index.html.
